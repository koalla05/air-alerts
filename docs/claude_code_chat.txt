⏺ Found the bug: px.choropleth with a categorical color column creates two
  separate traces (one per status group) sharing the same geojson/fitbounds.
  With two traces on one geo subplot, Plotly's fitbounds="locations" computation
  breaks — it doesn't union the traces' bounds correctly, so one trace balloons
  to fill the whole canvas while the other renders as a tiny unfitted outline.
  That matches the screenshot exactly (full red fill + one stray bordered
  shape).

  Fix: use a single go.Choropleth trace with a numeric indicator and a 2-color
  discrete colorscale instead of a categorical color column, plus dummy legend
  traces to keep the legend.

⏺ Found it — the polygon renders as a white hole, while the entire bounding
  rectangle gets filled with color. This is the classic GeoJSON winding-order
  bug: Plotly's geo renderer (d3-geo) requires exterior rings to be
  counter-clockwise per the RFC 7946 spec; if a ring is wound clockwise, the
  fill inverts — treating the polygon's inside as a hole and the rest of the
  world as "inside". Let me confirm.

  Read 1 file, ran 2 shell commands (ctrl+o to expand)

⏺ The bug is winding order: the exterior rings in
  data/geo/ukraine_oblasts.geojson are wound the opposite way from what Plotly's
  renderer (d3-geo) expects, so it fills everything except the oblasts instead
  of the oblasts themselves. I'll fix this in load_ukraine_geojson() so it
  self-corrects regardless of how the source file is wound.

  Root cause: data/geo/ukraine_oblasts.geojson has its polygon rings wound in
  the direction opposite to what Plotly's geo renderer expects. This causes the
  renderer to invert the fill — painting the entire world/bounding box red
  instead of just the oblasts, with each oblast appearing as an unfilled "hole"
  (that stray border you saw in the screenshot).

  Fix: added _rewind_ring/_rewind_geometry to map.py (src/alertpred/app/map.py),
  applied in load_ukraine_geojson(), which reverses every ring's point order
  before Plotly sees it. No changes needed to the data file itself or to the
  rest of the plotting logic — confirmed with a kaleido-rendered PNG that
  regions now render individually with correct colors and visible borders.

❯ Great. Now lets go to the most valuable part of app - the data processing,
  data training and inference for current state predictions. What are your
  suggestions for training on the data we have? The problems we faced are two
  different data sources, the gap of 7 days in September without data (can be
  mitigated using the third data source, for example volunteer dataset from the
  same github repository), and the division on raions instead of complete
  oblasts.

⏺ Three separate problems, and I'd treat them differently rather than solve them
  uniformly:

  Two sources (GitHub CSV + alerts.in.ua): Keep them layered, not merged as
  equals — GitHub is the deep-history backbone, alerts.in.ua's month_ago fills
  the recent tail, each row keeps its source tag (already the case in
  backfill.py). Low risk, already basically built.

  The 7-day gap: Pulling in the volunteer dataset from the same repo to patch
  just that window is reasonable — same trusted source, narrow scope, easy to
  validate against the neighboring days on either side the way we validated the
  alerts.in.ua backfill.

  The granularity shift — this is the one that actually matters for model
  quality, more than the gap. It's not just missing data, it's a regime change:
  a pre-Nov-2025 "oblast active" episode meant a blanket siren across the whole
  oblast; our raion-rollup "oblast active" signal means "at least one of ~7
  raions has a localized threat" — structurally different duration
  distributions. Concatenating both eras into one training set would blend two
  different phenomena and bias the model toward a regime that no longer exists,
  while production inference is now served entirely in the new regime.

  My recommendation: don't train raion-level models yet — we only have ~30 days
  of raion history, which is too thin per-raion for even the empirical
  baselines. Keep training at oblast granularity, but segment by regime and
  weight toward the current one — either a hard cutover to post-shift data for
  the production model (small sample, so stick with the empirical/Kaplan-Meier
  baselines rather than LightGBM, consistent with PLAN.md's "ladder of models")
  with the full history kept only as a reference comparison, or a
  recency-weighted single model. Raion-level training becomes viable once our
  own poller (this is the moment PLAN.md's "run your own poller" item earns its
  keep) has accumulated a few months of raion history.

  Which of those two — hard regime cutover vs. recency-weighted single model —
  appeals more, or do you want to see both compared on the test split before
  deciding?

  max_duration_hours (72 hours = 3 days) gets dropped from the cleaned dataset,
  on the assumption that a real air-raid alert essentially never runs

  artifact, not a real event.

  clean_alerts() function before I touched anything (paired with the
  min-duration filter: min_duration_sec=60 drops sub-minute glitches at the

  fetch_all_region_histories() for consistency across all three cleaning paths —
  that third one is exactly what caught and removed the bogus 31-day

  It's a reasonable threshold in practice: even the most sustained real activity

⏺ Testing here is built around one core trick: one real, completed alert gets
  turned into many synthetic "test moments."

  The real example above: a Kharkiv alert that started 2026-09-04 09:52:37 and
  ended 11:23:57 — 91.33 minutes total, known only because it's in the past and
  we have the full record. sample_as_of_alert_moments replays it at checkpoints
  (0, 5, 10, 15, 20, 30, 45, 60, 90 min elapsed — 120 is skipped since the alert
  had already ended by then):

  ┌──────────────┬───────────────────────┬─────────────────────────────────┐
  │  Simulated   │  elapsed_min (model   │  target_remaining_min (hidden   │
  │    "now"     │      sees this)       │           from model)           │
  ├──────────────┼───────────────────────┼─────────────────────────────────┤
  │ 09:52:37     │ 0                     │ 91.3                            │
  ├──────────────┼───────────────────────┼─────────────────────────────────┤
  │ 10:22:37     │ 30                    │ 61.3                            │
  ├──────────────┼───────────────────────┼─────────────────────────────────┤
  │ 10:52:37     │ 60                    │ 31.3                            │
  ├──────────────┼───────────────────────┼─────────────────────────────────┤
  │ 11:22:37     │ 90                    │ 1.3                             │
  └──────────────┴───────────────────────┴─────────────────────────────────┘

  The key boundary: at each row, the model only gets what someone opening the
  app at that exact moment could actually know — region, elapsed time,
  hour-of-day, how many alerts hit this region in the last 6/24h before that
  moment. It never sees finished_at or the true total duration — that's
  reconstructed from hindsight purely to create the label. This is why PLAN.md
  insists on an explicit as_of_ts: every feature must be computable using only
  data with a timestamp before it, or you leak the answer into the input.

  Prediction vs. comparison: for each row, the model outputs P10/P50/P90 for
  remaining time. At the 60-min-elapsed row, if it predicts P50=35, the true
  answer was 31.3 — that 3.7-minute error feeds into MAE; the full P10/P50/P90
  triple feeds into pinball loss (penalizes being wrong, penalizes it more if
  you're wrong on the wrong side of your own quantile); and coverage_p10_p90
  checks whether 31.3 actually fell inside the model's [P10, P90] band,
  aggregated over thousands of rows — if the model says "P10–P90" and only 50%
  of true values land inside instead of ~80%, the uncertainty band is
  miscalibrated, not just the point estimate.

  Why chronological split, not random: create_time_split cuts by date — train on
  older episodes, test on the most recent ones (in notebook 02, the last 21
  days). A random shuffle would let the model train on an alert from October and
  get tested on one from September, which is unrealistic — the app will only
  ever predict forward from "now" using what already happened, never the
  reverse. The chronological split is the honest simulation of "deploy this
  model today, see how it does on the next 3 weeks."

  Task B (time to next alert) works identically, just flipped: checkpoints are
  sampled through the quiet gap between two alerts (elapsed_quiet_min = 0, 30,
  60, 120, 240, 480...), target = true total gap minus elapsed, same
  pinball/coverage evaluation.

  The alternative — just running the model forward through the test window and
  checking if it called "active/inactive" right at each real timestamp — isn't
  used here because the actual product question isn't classification, it's
  "given this alert has already run for 60 minutes, how much longer?" — which
  only the as-of sampling actually tests.

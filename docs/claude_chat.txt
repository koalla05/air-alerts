I’ve put the plan in PLAN.md, ready to drop into your repository.

Framing: Both predictions are time-to-event problems, not classic forecasting. The app has to answer “given the alert has already lasted t minutes, when does it end?”, and survival analysis handles that conditional question and the censoring of still-active alerts.

Models: Build baselines first (empirical conditional median and Kaplan–Meier), then LightGBM quantile regression, which gives the P10/P50/P90 ranges the UI needs. After that, add a discrete-time hazard model for proper probability curves such as “ends within 30 min: 41%”. Weibull AFT serves as an interpretable benchmark. Hawkes processes and graph neural networks are listed as stretch goals.

Most valuable features: Neighbor-region states, such as alerts propagating between oblasts, should matter most, so build them early.

Data: The plan uses the alerts.in.ua API for live status plus a community historical dataset. Start polling and storing your own data on day 1. Check the API’s current access and terms of use before relying on it.

App: Streamlit with Plotly (PyDeck as an upgrade) gives a dark-themed map, a region panel with prediction ranges and curves, a 24-hour timeline strip, and a data-freshness indicator.

The file also covers evaluation (time-based splits only, calibration checks, leakage tests), a repo structure, a phased roadmap with checklists, risks, and a definition of done for the MVP. I included a disclaimer that this is a statistical experiment and not a safety tool, and I’d keep it visible in the UI.

When you’re ready to start coding, I’d suggest beginning with Phase 0 and Phase 1, the region mapping and the poller, since the poller needs to run as early as possible to build up your own dataset.
